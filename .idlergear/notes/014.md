RAG retriever optimization issues created

Based on slot retriever benchmark analysis (20260103_081055) and conversation history, created 6 GitHub issues for FAISS-optimized retrieval implementations:

**Conservative Tuning (Safe for 16GB+ systems):**
- #181 [P1-Conservative]: Optimized FAISS (2.9GB, 88-90% recall, 3-4ms)
  - Fix nlist calculation (65K vs √N)
  - HNSW quantizer instead of flat
  - Runtime-tunable nprobe/efSearch
  
- #182 [P2-Conservative]: FusedMultiSlot (2.4GB, 85-90% recall, 1-2ms)
  - Weighted fusion instead of intersection
  - Parallel slot queries (3 threads)
  - Recovers 10-15% recall lost by MultiFAISS

- #183 [P3-Conservative]: Cached Mmap (876MB, 90% recall, 2-5ms cached)
  - LRU cache for hot embeddings (10K docs)
  - Best accuracy, lowest memory
  - Good for repeated query patterns

**Aggressive Tuning (Leverages 30GB RAM + 16 cores):**
- #184 [P1-AGGRESSIVE]: FAISS + 16-core multi-threading (4.5GB, 92-95% recall, 2-3ms)
  - M=48 HNSW graph, efConstruction=80
  - Query result cache (50K, ~800MB)
  - faiss.omp_set_num_threads(16)

- #185 [P2-AGGRESSIVE]: FusedMultiSlot massive parallelism (7.4GB, 88-92% recall, 5000+ q/s)
  - 15 thread workers + 8 process workers
  - Dual caching (query + fusion, 200MB each)
  - Highest throughput option

- #186 [P3-AGGRESSIVE]: Cached Mmap multi-level cache (5.2GB, 90% recall, 0.1ms median)
  - L1 (100K) + L2 (2.4M docs = 60% corpus)
  - 99% cache hit rate
  - Query log analysis for intelligent preloading
