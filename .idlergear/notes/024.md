# Klareco Retriever Implementations - Complete Overview

## IMPLEMENTED RETRIEVERS (6 total)

### 1. Retriever (klareco/rag/retriever.py)
**Type**: Simple sentence-level semantic search  
**Architecture**: SemanticPipeline (Stage 1 compositional embeddings) + FAISS  
**Status**: ⚠️ DEPRECATED - replaced by slot-based retrievers  

**Pros**:
- Simple architecture
- Fast (FAISS-backed)

**Cons**:
- Averages all word embeddings (loses AST structure)
- No role awareness (SUBJ/VERB/OBJ)
- Low recall (~35% baseline)

**Should you use it?**: ❌ NO - slot-based retrievers are strictly better

---

### 2. SlotBasedRetriever (klareco/rag/slot_retriever.py) ⭐
**Type**: Two-stage slot-aware retrieval (naive in-memory)  
**Architecture**: Stage 1 slot filtering + Stage 2 full reranking  
**Benchmark**: 85% recall, 11.5ms latency (1K docs)  

**Pros**:
- ✅ Role-aware matching (SUBJ/VERB/OBJ separate embeddings)
- ✅ Highest accuracy for small indexes
- ✅ Simple implementation
- ✅ Good for testing/demos

**Cons**:
- ❌ Loads ALL docs in memory (unusable for 4M+ docs)
- ❌ No disk-backed storage

**Should you use it?**: ✅ YES for indexes <100K docs  
**Current usage**: Test indexes, benchmarks

---

### 3. FAISSSlotRetriever (klareco/rag/slot_retriever_faiss.py) ⭐⭐⭐
**Type**: FAISS pre-filtering + slot reranking  
**Architecture**: FAISS ANN on full embeddings → slot scoring  
**Benchmark**: 85% recall, 5.1ms latency, 3.3MB memory delta  

**Pros**:
- ✅ **Memory-efficient** (disk-backed FAISS index)
- ✅ **Fast** (5.1ms - 9x faster than mmap)
- ✅ **Scales to millions of docs**
- ✅ GPU support available

**Cons**:
- Slightly lower MRR than mmap (0.775 vs 0.860)
- Requires FAISS index pre-built

**Should you use it?**: ✅ **YES - RECOMMENDED for production**  
**Current usage**: Auto-selected by demo for indexes >100K docs  
**Best for**: Large-scale retrieval (100K - 10M docs)

---

### 4. MemoryMappedSlotRetriever (klareco/rag/slot_retriever_mmap.py)
**Type**: Memory-mapped numpy arrays + lazy loading  
**Architecture**: mmap for embeddings, lazy doc loading  
**Benchmark**: 90% recall, 44.8ms latency, 4.3MB memory delta  

**Pros**:
- ✅ **Highest recall** (90%)
- ✅ **Highest MRR** (0.860)
- ✅ Low memory delta (4.3MB)

**Cons**:
- ❌ **Slowest** (44.8ms - 9x slower than FAISS)
- ❌ Auto-skipped for indexes >1M docs (too slow)

**Should you use it?**: ⚠️ MAYBE for medium indexes (10K-100K docs) where accuracy > speed  
**Current usage**: Benchmarks only  
**Best for**: Offline batch processing where 90% recall matters

---

### 5. MultiFAISSSlotRetriever (klareco/rag/slot_retriever_multifaiss.py)
**Type**: Separate FAISS index per slot (SUBJ, VERB, OBJ)  
**Architecture**: 3 FAISS indexes + intersection/union merge  
**Benchmark**: 75% recall, 1.1ms latency (fastest!)  

**Pros**:
- ✅ **Fastest** (1.1ms - 5x faster than FAISSSlotRetriever)
- ✅ Memory-efficient
- ✅ Slot-level query optimization

**Cons**:
- ❌ **Lowest recall** (75% - 10% worse than FAISS)
- ❌ Lowest MRR (0.559)
- ❌ Complex index management

**Should you use it?**: ⚠️ MAYBE for ultra-low latency use cases where 75% recall acceptable  
**Current usage**: Benchmarks only  
**Best for**: Real-time autocomplete, suggestions (not primary retrieval)

---

### 6. SQLiteSlotRetriever (klareco/rag/slot_retriever_sqlite.py)
**Type**: SQLite backend with BLOB embeddings  
**Architecture**: SQLite for metadata + embeddings as BLOBs  
**Benchmark**: 85% recall, 30.9ms latency, 5.4MB memory delta  

**Pros**:
- ✅ SQL query support (filter by source, tier, etc.)
- ✅ Transactional updates
- ✅ Familiar tooling

**Cons**:
- ❌ Slower than FAISS (30.9ms vs 5.1ms)
- ❌ Higher memory delta (5.4MB)
- ❌ More complex for simple vector search

**Should you use it?**: ⚠️ MAYBE if you need SQL filtering + vector search combined  
**Current usage**: Benchmarks only  
**Best for**: Hybrid search (keywords + vectors + metadata filters)
