# SQLiteSlotRetriever Performance Analysis

## Current Architecture
- SQLite database stores documents with BLOB embeddings
- Indexed columns: negita, tempo, fraztipo (for feature filtering)
- Current benchmark: 85% recall, 30.9ms latency, 5.4MB memory delta

## Critical Performance Issues Found

### 🔴 PROBLEM 1: Processes ALL docs (or prefilter_limit) every query
**Location**: Lines 280-295 (SQL query), 300-342 (scoring loop)

**Issue**: 
- SQL query returns first `prefilter_limit` (default 5000) documents
- Then processes ALL 5000 in Python loop
- **No semantic pre-filtering** - just arbitrary LIMIT

**Evidence**:
```python
sql = f"""SELECT ... FROM documents
    {"WHERE " + " AND ".join(where_clauses) if where_clauses else ""}
    LIMIT {prefilter_limit}"""  # ❌ Just takes first 5000!
```

**Impact**: Processes 5000 docs × 3 slots = 15,000 similarity calculations per query

**Similar to**: MemoryMappedSlotRetriever (processed all 4.2M)

---

### 🔴 PROBLEM 2: Non-vectorized slot similarity
**Location**: Lines 180-206 (slot_similarity), 300-342 (search loop)

**Issue**:
- Nested Python loops: for each doc → for each slot → cosine_similarity
- Recomputes norms every call (line 172-173)
- No batch processing

**Evidence**:
```python
for row in rows:  # ❌ Python loop over 5000 docs
    for slot, weight in self.slot_weights.items():  # ❌ Python loop over 3 slots
        sim = self.cosine_similarity(query_emb, doc_emb)  # ❌ Recomputes norms
```

**Impact**: 5000 docs × 3 slots = 15,000 Python iterations + norm recomputations

**Similar to**: MemoryMappedSlotRetriever before vectorization (#209)

---

### 🟡 PROBLEM 3: No pre-computed norms
**Location**: Lines 170-178 (cosine_similarity)

**Issue**:
- Computes `np.linalg.norm(a)` and `np.linalg.norm(b)` every call
- For 5000 docs × 4 embeddings (SUBJ/VERB/OBJ/full) = 20,000 norm computations

**Evidence**:
```python
def cosine_similarity(self, a: np.ndarray, b: np.ndarray) -> float:
    norm_a = np.linalg.norm(a)  # ❌ Recomputed every time
    norm_b = np.linalg.norm(b)  # ❌ Recomputed every time
```

**Impact**: 20K+ norm computations per query (wasteful)

**Similar to**: MemoryMappedSlotRetriever before pre-normalization (#210)

---

### 🟡 PROBLEM 4: BLOB deserialization overhead
**Location**: Lines 303-308 (embedding extraction)

**Issue**:
- Every query deserializes BLOBs for 5000 docs × 4 embeddings = 20,000 deserializations
- `np.frombuffer()` called repeatedly

**Evidence**:
```python
for row in rows:  # ❌ 5000 iterations
    doc_slots = {
        'SUBJ': self._blob_to_embedding(row['subj_embedding']),  # ❌ Deserialize
        'VERB': self._blob_to_embedding(row['verb_embedding']),  # ❌ Deserialize
        'OBJ': self._blob_to_embedding(row['obj_embedding']),    # ❌ Deserialize
    }
    full_emb = self._blob_to_embedding(row['full_embedding'])  # ❌ Deserialize
```

**Impact**: 20K BLOB deserializations per query

**Unique to**: SQLite retriever

---

### 🔵 PROBLEM 5: Unused SQL feature prefilter
**Location**: Lines 272-278, 288

**Issue**:
- `use_feature_prefilter` parameter exists but does nothing
- WHERE clause never built (lines 275-278 is just `pass`)
- Missing opportunity for SQL-side filtering

**Evidence**:
```python
if use_feature_prefilter:
    # Exact matches preferred, but also allow non-matches
    # This is a soft filter - we'll use it for scoring
    pass  # ❌ Not implemented!
```

**Impact**: Could filter at SQL level (faster than Python)

**Unique to**: SQLite retriever

---

### 🟢 PROBLEM 6: No connection pooling
**Location**: Line 65 (single connection)

**Issue**:
- Single SQLite connection created at init
- Not a problem for single-threaded use
- Would be bottleneck for concurrent queries

**Impact**: Minor (only affects multi-threaded usage)

## Optimization Opportunities

### P0: Add FAISS pre-filtering before SQL query
**Expected impact**: 15x speedup (30.9ms → 2ms)

**Approach**:
1. Add FAISS index on full embeddings (reuse from FAISSSlotRetriever)
2. Stage 0: FAISS → top 500 candidates (2ms)
3. Stage 1: SQL query with `WHERE id IN (...)` for those 500 docs only
4. Stage 2: Slot scoring on 500 docs (vs current 5000)

**Complexity**: Medium (requires FAISS setup)

---

### P1: Pre-compute and store norms in database
**Expected impact**: 15-20% speedup

**Approach**:
1. Add columns: `subj_norm`, `verb_norm`, `obj_norm`, `full_norm`
2. Compute during `_create_db()`
3. Load in query, avoid recomputing

**Complexity**: Low (schema change + migration)

---

### P1: Batch BLOB deserialization
**Expected impact**: 10-15% speedup

**Approach**:
1. Deserialize BLOBs to numpy arrays in batches
2. Use vectorized operations (similar to #209 fix)
3. Reduce Python loop overhead

**Complexity**: Medium (requires vectorization)

---

### P2: Implement SQL feature prefilter
**Expected impact**: 5-10% speedup (if features selective)

**Approach**:
1. Build WHERE clause from query features
2. Use indexed columns (negita, tempo, fraztipo)
3. Reduce candidates before slot scoring

**Complexity**: Low (just implement the WHERE clause logic)

---

### P2: Add connection pooling for multi-threading
**Expected impact**: Enables concurrent queries

**Approach**:
1. Use `sqlite3.connect(..., check_same_thread=False)`
2. Add threading locks
3. Or use connection pool library

**Complexity**: Low (only needed for multi-threaded apps)

## Recommended Priority

1. **P0: FAISS pre-filtering** (#213) - Biggest win, 15x speedup
2. **P1: Pre-compute norms** (#214) - Quick win, 15-20% speedup
3. **P1: Vectorize + batch BLOB deser** (#215) - Medium effort, 10-15% speedup
4. **P2: Implement SQL feature filter** (#216) - Easy, 5-10% speedup if selective
5. **P3: Connection pooling** - Only if multi-threading needed

**Combined expected performance**:
- Current: 30.9ms
- With all optimizations: ~2-3ms (10-15x speedup)
- Would make SQLite competitive with FAISSSlotRetriever!

## Key Insight

SQLite retriever has **same fundamental problem** as MemoryMappedSlotRetriever before fixes:
- Processes too many candidates (5000 vs optimal ~500)
- Non-vectorized Python loops
- Recomputes norms repeatedly

But it has **unique advantage**: SQL filtering could be powerful if properly implemented.

**Hybrid SQLite + FAISS** could be interesting:
- FAISS for semantic pre-filtering
- SQL for metadata filtering (source, tier, date ranges, etc.)
- Best of both worlds for complex queries!
