## AST-Aware Retrieval System - Implementation Plan

I've created 5 tasks (#49-53) to implement the ideal AST-aware retrieval strategy that leverages our unique advantage of having fully parsed structures.

### Task Dependency Chain

```
Task #49: Question Classifier (4 hrs)
    ↓
Task #50: AST Pattern Matcher (8 hrs) ←──┐
    ↓                                      │
Task #51: Semantic Relation DB (6 hrs) ───┤
    ↓                                      │
Task #52: Entity Recognizer (6 hrs) ──────┤
    ↓                                      │
Task #53: Multi-Strategy Retriever (10 hrs)
```

**Total Sequential Effort**: ~44 hours
**Parallelizable**: Tasks #50, #51, #52 can run in parallel after #49 → ~28 hours

### Key Innovation: Exploit Structure, Not Just Embeddings

**Current System** (BROKEN):
- Relies on embeddings to capture everything
- Rigid slot matching (SUBJ/VERB/OBJ must align)
- Single strategy (slot similarity)
- **Result**: 10-12% accuracy

**New System** (DESIGNED):
- **4 parallel strategies** with different strengths
- **Deterministic** pattern matching (exploits AST)
- **Flexible** structural matching (handles fragments, passives)
- **Entity-aware** (recognizes WHO/WHAT/WHERE/WHEN)
- **Embeddings as fallback** (not primary strategy)

### Why This Will Work

1. **Handles fragments without verbs**
   - Current: "ZAMENHOF, Aŭtoro de Esperanto" → no verb → fails
   - New: Pattern matcher recognizes appositive → matches!

2. **Question-type specific**
   - WHO questions → boost docs with person entities
   - WHEN questions → boost docs with dates/years
   - WHAT (definition) → look for "X estas Y" patterns

3. **Synonym-aware**
   - fondis ≈ kreis ≈ "esti aŭtoro de"
   - Semantic relation DB provides this

4. **Multi-strategy robustness**
   - If pattern fails → entity search might work
   - If entity fails → semantic role might work
   - If all fail → embeddings provide baseline

### Example Walkthrough: "Kiu fondis Esperanton?"

**Question Classifier** (Task #49):
- Type: WHO
- Seeking: PERSON
- Intent: entity_action

**Pattern Matcher** (Task #50):
Generates patterns:
1. `{PERSON} fondis Esperanton` (active)
2. `{PERSON}, fondinto de Esperanto` (appositive)
3. `{PERSON}, aŭtoro de Esperanto` (synonym)
4. `Esperanto estis fondita de {PERSON}` (passive)

**Entity Recognizer** (Task #52):
- Query entities: ["Esperanto"]
- Seeking: PERSON entity
- Filters: docs with "Esperanto" + PERSON entity

**Semantic Relation DB** (Task #51):
- fond → [krei, establi, "esti aŭtoro de"]
- Expands search to semantic equivalents

**Multi-Strategy Retriever** (Task #53):
Parallel search:
- Pattern: Finds "ZAMENHOF, Aŭtoro..." (appositive pattern match)
- Entity: Finds docs with "Esperanto" + "ZAMENHOF" (person)
- Role: Finds docs with agent="ZAMENHOF" + theme="Esperanto"
- Embedding: Baseline fallback

**Final Score**:
- Pattern match: 2.0 × 0.95 = 1.90
- Entity match: 1.5 × 3.5 = 5.25 (entity overlap + person type)
- Has PERSON entity: +1.0
- **Total**: 8.15 vs irrelevant doc (~0.3)

### Comparison to Embedding Investigation (Tasks #40-48)

These are **complementary** approaches:

**Embedding Investigation** (#40-48):
- Diagnoses **why current system fails**
- Identifies if embeddings are collapsed
- Quantifies the problem
- Recommends fixes to embeddings

**AST-Aware Retrieval** (#49-53):
- **Bypasses embedding weaknesses** with deterministic methods
- Uses AST structure we already have
- Provides immediate improvement
- Makes system **explainable**

**Recommendation**: 
1. Start with AST-aware retrieval (#49-53) for immediate ~5x accuracy boost
2. Run embedding investigation (#40-48) in parallel to improve fallback strategy
3. Iterate: improve both deterministic and learned components
