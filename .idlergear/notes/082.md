## Decision: Deleted Non-Memory-Efficient Retrievers (2026-01-06)

### What Was Deleted

1. **SlotBasedRetriever** (`klareco/rag/slot_retriever.py`)
   - Problem: O(n) linear scan of ALL 4.4M documents per query
   - Impact: Hours per query (unusable for production)
   - Had lazy loading for memory, but time complexity was O(n)

2. **Retriever (legacy)** (`klareco/rag/retriever.py`)
   - Problem: Loaded ALL metadata into RAM at startup
   - Impact: OOM crash (~10-15GB RAM for 4.4M docs)
   - Did not use AST slots (legacy approach)

### Why Delete Instead of Fix

- Both retrievers would need significant refactoring to add prefilters
- We already have 8 production-ready retrievers that handle 4.4M corpus
- Keeping broken code creates confusion about which retrievers to use
- The slot matching logic lives in the working retrievers anyway

### Production Retrievers (Memory Efficient)

| Retriever | Latency | Recall | Best For |
|-----------|---------|--------|----------|
| ASTAwareRetriever | ~0.4s | ~85% | Q&A with full AST analysis |
| HNSWSlotRetriever | ~2-3ms | ~85-90% | Fastest retrieval |
| FAISSSlotRetriever | ~5ms | ~85% | Good balance |
| HybridFAISSMmapRetriever | ~3.5ms | ~90% | Best accuracy |
| ScaNNSlotRetriever | ~3-5ms | ~90-95% | Highest recall |
| MultiFAISSSlotRetriever | ~8ms | ~88% | Per-slot search |
| SQLiteSlotRetriever | ~10ms | ~80% | All on disk |
| MemoryMappedSlotRetriever | Medium | ~90% | Pure mmap |
