# Dual-Embedding Prefilter Strategy

## Problem
- HNSW index uses 128d HybridEmbeddings (64d linguistic + 64d topical)
- SemanticPipeline produces 64d embeddings with trained affix transforms
- Dimension mismatch causes SemanticPipeline to be bypassed → losing morphological understanding

## Solution: Cascade Architecture

### Stage 1: HNSW Coarse Retrieval (128d Hybrid)
- Use HybridEmbeddings for fast vectorized search
- Good for: topical similarity, proper nouns (Wikipedia entities)
- Retrieves k=500 candidates (O(log n) search)

### Stage 2: Semantic Slot Reranking (64d SemanticPipeline)
- Use SemanticPipeline with trained affix transforms
- Leverages morphological understanding (re-hundo ≈ hundo, fondis → fondinto)
- Slot-aware: Compare SUBJ↔SUBJ, VERB↔VERB, OBJ↔OBJ
- Question-type-aware weighting (WHO → SUBJ weight, WHERE → OBJ weight)

### Key Insight
The two embedding spaces serve **different purposes**:
- HybridEmbeddings (128d): Topical/distributional similarity
- SemanticPipeline (64d): Morphological/compositional similarity

**Use both in cascade, not either/or!**

### Implementation
1. `_hnsw_prefilter()`: Uses 128d for initial retrieval (already working)
2. `_compute_slot_similarity()`: Add SemanticPipeline for slot embeddings
3. Extract slots from query AST using SemanticPipeline (not hybrid_embedder)
4. Reparse document ASTs and compute 64d slot embeddings for comparison

### Alternative: Pre-computed Dual Slots
Store both 128d and 64d slot embeddings in index:
- `slots_hybrid`: 128d for HNSW retrieval
- `slots_semantic`: 64d for fine-grained reranking
This avoids runtime re-embedding of documents.
