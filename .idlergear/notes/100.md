# Dual-Embedding Implementation Results

## What Was Implemented
1. **SemanticPipeline semantic boost** in `_compute_semantic_boost()`:
   - Uses 64d SemanticPipeline with trained root+affix transforms
   - Computes max-similarity matching between query and document words
   - Works correctly: exact match=1.0, synonym=0.16, non-match=0.10

2. **Three-way score combination** in HNSW prefilter:
   - HNSW (20%) + Slot (50%) + Semantic boost (30%)
   - Semantic boost added to both HNSW and keyword prefilters

## Benchmark Results
- Recall@10: 5.9% (unchanged)
- Latency: 674ms (improved from 745ms)
- F1: 0.108 (unchanged)

## Why No Improvement in Recall
The semantic boost only affects **reranking** of already-retrieved candidates.
The bottleneck is **coarse retrieval** (HNSW search):
- HNSW searches 4.37M vectors with 128d query embedding
- If relevant docs aren't in top-K candidates, reranking can't help
- 64d SemanticPipeline embeddings can't be used directly for HNSW (dimension mismatch)

## Root Cause Analysis
The 5.9% Recall@10 means relevant docs aren't being found in initial retrieval.
This could be due to:
1. HybridEmbeddings (128d) not capturing semantic similarity for benchmark queries
2. Corpus may not contain documents with expected answers
3. Query embedding doesn't match document embedding space

## Next Steps
1. **Build dual-index architecture**: 
   - 128d HNSW for topical similarity (current)
   - 64d HNSW for morphological similarity (new)
   - Merge results from both before reranking

2. **Investigate corpus coverage**:
   - Check if benchmark answer documents exist in corpus
   - Verify document embeddings match expected similarity

3. **Alternative: Keyword fallback before HNSW**:
   - Use keyword prefilter to ensure base recall
   - Then apply semantic boost for ranking
